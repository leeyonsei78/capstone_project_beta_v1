# 계정 탈취(ATO) LLM 방어 예비 실험 설계안 (초안)

2026-11-16 작성. 구현 전 설계 문서이며 사전 등록이 아니다. 아래 "열린 결정" 항목이 확정되기 전에는 코드를 작성하지 않는다.

## 1. 연구 질문

- RQ1. 로그인 이벤트와 계정 이력을 본 LLM이 `allow / challenge / lock` 중 고른 조치는 단순 임계값 규칙보다 탈취 차단과 정상 사용자 보호를 더 잘 균형 잡는가.
- RQ2. LLM 판단 지연(동기/비동기, 도착률)이 탈취 성공 건수에 어떤 영향을 주는가. SQL 재생 실험의 `RPS × 추론시간` 노출 모델이 여기에도 성립하는가.
- RQ3. 결과가 모델(Qwen 외)과 독립 작성 사례에서도 유지되는가.

SQL 실험과 달리 이 실험의 핵심은 LLM의 실제 판단력이다. 정답이 한 가지로 정해지지 않는 경계 사례가 평가의 중심이다.

## 2. 범위와 비범위

범위: loopback의 가상 인증 서버, 가상 계정, 합성 이벤트 재생. 공격 이벤트는 사전에 정의한 고정 시퀀스이며 AI 공격자를 호출하지 않는다. 외부 서비스, 실제 계정, 실제 크리덴셜 목록은 사용하지 않는다.

비범위: 적응형 공격자, 실제 이메일/SMS 발송, 실제 서비스 로그의 성능 주장, 운영 환경 오탐률 추정.

## 3. 입력 이벤트 스키마

계정별 이력은 요약 형태로 모델에 제공한다 (원문 전체를 넣지 않는다).

| 필드 | 설명 | 신뢰 수준 |
|---|---|---|
| `account` | 가상 계정 ID | 서버 생성 |
| `event_type` | login / password_reset / mfa_fail / session_use | 서버 생성 |
| `credential_ok` | 비밀번호 일치 여부 | 서버 생성 |
| `ip_asn`, `geo` | 출발지 네트워크·대략 지역 (가상 값) | 서버 생성 |
| `device_known` | 이전에 본 기기 지문인지 | 서버 생성 |
| `local_hour` | 계정 기준 현지 시각 | 서버 생성 |
| `recent_fail_count` | 최근 윈도 내 해당 계정 실패 수 | 서버 집계 |
| `ip_distinct_accounts` | 같은 IP가 시도한 서로 다른 계정 수 | 서버 집계 |
| `account_profile` | 평소 지역·기기 수·로그인 시간대 요약 | 서버 집계 |
| `user_agent`, `username` | 클라이언트 제공 문자열 | **비신뢰 데이터** (프롬프트 주입 가능성, 데이터로만 취급) |

## 4. 방어 조치 (LLM 출력)

JSON 스키마 `{"action": "allow|challenge|lock"}` 하나로 제한한다 (이유 문장은 받지 않아 출력 길이와 주입 표면을 줄인다).

- `allow`: 통과.
- `challenge`: 추가 인증 요구. 시뮬레이션에서 정당한 사용자는 통과, 공격자는 실패로 정의한다. 정상 사용자에게는 마찰 비용 1.
- `lock`: 계정 잠금. 정상 사용자에게는 마찰 비용 5 (가중치는 열린 결정).

LLM이 `lock`을 남발하면 DoS가 되므로, 정상 사용자 마찰을 성공 지표와 같은 비중으로 보고한다.

## 5. 시나리오 구성

### 5.1 정상 (레이블: benign)

- 익숙한 기기·지역의 일상 로그인
- 비밀번호 1~3회 오입력 후 성공
- 출장·여행 (새 지역, 기존 기기)
- 새 기기 교체 (같은 지역)
- VPN/이동통신 IP 변경
- 야간 근무자의 비정상 시간대 로그인
- 공유 NAT(사무실)에서 여러 계정 정상 로그인 ← IP 규칙 오탐 유도

### 5.2 공격 (레이블: attack)

- 크리덴셜 스터핑: 한 IP가 다수 계정에 시도
- 저속 password spray: 계정당 소수 시도, 긴 간격 분산 IP
- 탈취된 세션 재사용: 짧은 시간에 먼 지역에서 session_use
- 비밀번호 재설정 남용 후 새 기기 로그인
- 정상 위장: 올바른 크리덴셜, 같은 국가, 새 기기, 평소 시간대 (가장 어려운 경계 사례)

### 5.3 경계 사례의 정답 정의

경계 사례는 `허용 조치 집합`으로 정의한다 (예: 출장 로그인은 {allow, challenge} 허용, lock은 오조치). 정답이 단일 값이라고 가정하지 않는다.

## 6. 비교 조건

| 조건 | 설명 |
|---|---|
| `none` | 항상 allow |
| `rules` | 임계값 규칙 (실패 N회 → lock, 새 지역 → challenge 등). 규칙 자체는 개발 사례를 보기 전에 고정한다 |
| `always_challenge` | 모든 로그인 challenge (마찰 상한 대조) |
| `llm_sync` | 이벤트마다 LLM 판단 후 처리 |
| `llm_async` | 요청은 먼저 처리, LLM 판단은 이후 반영 (SQL 실험과 동일 구조) |
| `llm_plus_rules` (선택) | 명백한 경우는 규칙, 경계만 LLM |

LLM은 이벤트 단위 판단과 계정 이력 요약 포함 판단을 구분해 두 변형을 비교할 수 있다 (열린 결정).

## 7. 평가 지표

- 탈취 성공: 공격 레이블 시퀀스에서 `allow`되고 credential_ok=true인 이벤트가 하나라도 있음
- 정상 마찰: benign 이벤트 중 challenge 비율, lock 비율, 가중 마찰 비용 합
- 경계 사례 정확도: 허용 조치 집합 내 비율
- 조치 지연: 이벤트 도착부터 조치 적용까지, 비동기 노출 구간에서 통과한 공격 이벤트 수
- 모델 실패는 failed로 분리하고 미실행 이벤트를 성공적 방어로 세지 않는다
- 반복은 변동 확인용이며 유의성 검정이나 모집단 신뢰구간을 산출하지 않는다

## 8. 외적 타당성 설계 (처음부터 반영)

- 사례 작성자와 평가자를 분리한다. 제3자가 5.1·5.2 범주별 사례를 별도로 작성한다.
- 데이터를 `dev`(프롬프트·규칙 설계에 사용)와 `holdout`(최종 평가 1회)으로 나눈다. holdout을 본 뒤 프롬프트·규칙을 수정하면 결과를 holdout으로 표기하지 않는다.
- 정상 트래픽은 공개 데이터셋 또는 실제 로그의 익명화 샘플을 쓰되, 이 저장소에는 가상 계정으로 변환한 값만 둔다.
- 규칙 조건의 임계값을 LLM에 유리하게 약하게 잡지 않았음을 보이기 위해, 규칙은 dev 사례를 보기 전 문서로 고정한다.

## 9. 반복·부하

- temperature=0, 모델 seed 고정, 반복마다 시퀀스와 조건 순서 셔플 (SQL 재생과 동일)
- 도착률 통제: `experiments/run_rate_sweep.py`의 open-loop 스케줄러 재사용. RPS 0.5, 1, 2, 5, 10
- 모델 비교는 `--model`만 교체. Ollama에서 받은 타 모델 1~2개

## 10. 구현 계획 (재사용 중심)

1. `ato_fixtures.py`: 스키마, dev 사례, 허용 조치 집합, 이벤트 집계 함수
2. `ato_study.py`: `ai_study.defend`와 같은 형태의 판단 함수와 `ACTION_SCHEMA`, 프롬프트(비신뢰 필드 분리)
3. `experiments/run_ato_replay.py`: 가상 인증 서버, 조건별 캠페인, manifest/JSON/CSV 저장
4. `test_ato_replay.py`: 취약(none)에서 공격 성공, `always_challenge`의 정상 마찰, 모델 실패 처리, 규칙 오탐 사례 확인
5. 도착률 스윕은 별도 실행 옵션으로 연결

## 11. 타당성 위협

- 합성 이벤트 분포가 실제와 다르다. 결과는 현실 효능이 아니라 방법 비교로만 해석한다.
- `challenge`의 성공/실패 정의가 시뮬레이션 가정이다.
- 이벤트 요약 방식(프롬프트 설계)에 결과가 민감할 수 있다. 요약 변형 간 비교를 보고한다.
- 사용자 마찰 가중치는 주관적이다. 가중치 민감도 분석을 함께 둔다.
- 동일 GPU 공유로 인한 지연 변동은 완전히 통제하지 않는다.

## 12. 열린 결정 (확정 필요)

1. 판단 단위: 이벤트 단위 / 계정 이력 요약 포함 / 둘 다
2. 마찰 가중치(challenge=1, lock=5)와 정답 허용 집합 정의
3. 사례 작성자 확보 방식 (제3자 또는 별도 LLM 생성 후 사람 검수)
4. 정상 트래픽 출처
5. `llm_plus_rules` 조건 포함 여부
6. dev/holdout 분할 비율과 사례 수 (제안: dev 30, holdout 30, 공격:정상 약 1:2)
